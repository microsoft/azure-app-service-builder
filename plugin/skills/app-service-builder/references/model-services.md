# Connections, model services and external dependencies

Read current [feature availability](https://builder.appservice.azure.com/docs/resources/feature-status/), [managed identity](https://builder.appservice.azure.com/docs/guides/managed-identity/), [external-service connections](https://builder.appservice.azure.com/docs/guides/connect-to-services/), [AI assistant guidance](https://builder.appservice.azure.com/docs/guides/host-ai-agent/), and [application variables](https://builder.appservice.azure.com/docs/guides/variables/) before recommending a model-backed app. Inspect the actual app/provider SDK contract, not just a service name.

## Explain the supported path first

Builder hosts the application, not the model or a managed agent service. An HTTP backend can call a separately owned, reachable HTTPS model service. Combined static frontend and HTTP backend is a documented app shape; private model credentials and model calls belong in the backend, not browser JavaScript.

**Check the current supported Connections service list first**, using the app-authorized catalog and maintained documentation rather than only this bundled inventory. **Recommend Builder Connections first** if the service is listed and its authentication/client path is supported. Use **Overview → Add connection** or **Architecture → Add connection**, rather than starting with manual Variables or asking for copied endpoints/keys. If the service is not listed, proceed with its standard SDK/API connection method and documented endpoint, identity/credential, and application configuration. Do not block a supported external service or force it into an unrelated Connections profile. A failed catalog lookup is not proof of absence; report the gap and check current docs. Both routes retain separate resource/access/configuration approvals, secure credential handling, deployment, and a real dependency-operation check.

Connections records an existing destination, exact runtime environment mappings, and a selected authentication mode; app code still uses its native SDK/driver. It does not provision a database/model, open networking, grant access merely by selecting an identity, or test connectivity.

The production catalog exposes **eleven enabled configuration profiles**: Blob Storage, Foundry inference, PostgreSQL, Azure SQL, Cosmos DB NoSQL, Key Vault, Managed Redis, Service Bus, Event Hubs, Application Insights and Connector Namespace. Managed-identity operation evidence covers Blob, Foundry and PostgreSQL with both identity types, plus bounded Application Insights ingestion with correlated telemetry. This is Preview target qualification, not permission for production workloads or every sample/authentication mode. Catalog presence or successful direct-variable service tests do not qualify named delivery. Protected modes and remaining sample journeys still need their own target verification; do not retain the obsolete blanket claim that all eight expanded profiles are unavailable. The public CLI release includes typed Connections; check installed service help rather than treating all CLI distribution as pending.

### Configure a connection through Portal

1. Inspect the existing app, desired and active connections, assigned identities, and the supported catalog. Select the service and existing resource in the user's chosen subscription/group; the destination need not share the app's resource group. Empty or failed discovery is not approval to create a resource or broaden access.
2. Select one assigned identity with committed current identifiers. Portal **Manage app identities** opens the app-wide Identity page; complete and observe that separate assignment before selection. The connection save itself does not assign or remove identities. Typed CLI setup can separately enable/attach the selected identity before saving, as described below; obtain assignment approval. For explicitly supported protected-credential mode, use its declaration instead, never both identity and credentials. Prefer passwordless access and preserve the destination's policy.
3. Match required and optional environment mappings to the actual app parser/SDK. Catalog suggestions and normal ARM metadata are not immutable names; preserve custom mappings. Optional blank rows are omitted. Resolve exact-name conflicts across manual variables, connections, protected mappings, and selected identity outputs before saving; `FOO` and `foo` are distinct. Generated identity fields are read-only. Ordinary discovery never fetches stored credentials or variable values.
4. **Add connection** or **Save** changes desired configuration only. Get separate approval for grants and deployment. Where offered, **Deploy after adding/saving** explicitly combines those reviewed effects; it rechecks credentials and assigned identities before one deployment. Missing/unreadable credential status or failed grants stops deployment, retains saved configuration, and offers scoped administrator instructions. Do not retry the entire setup or widen grants.
5. For a ZIP-backed app, save Connections first, then use **Versions → Upload ZIP and deploy** with a separately reviewed source archive. Recheck active version and a bounded real dependency operation afterward. **Needs setup**, **Not deployed**, and **Active** describe configuration/snapshot state; **Active** is not proof of a successful service request.

Edit mappings on the connection's Architecture **Variables** tab, and identity selection on its **Authentication** tab; the app-wide Variables page edits manual values only. Search destinations across accessible resource groups in the selected subscription; results identify `resource group / resource name`. Do not demand a resource-group name before discovery. Only declared Connections appear as Architecture nodes: manual endpoint variables do not register a node, and nodes are not live traffic/access proof. To change destination, add a new connection and remove the old one after reviewing the transition. Removal changes desired configuration, not active/retained snapshots, identities, or destination grants. Reads and Refresh never deploy.

Saves must respect the current app ETag and preserve unrelated fields. On conflict, refresh and reconcile ordinary draft settings; re-enter cleared credentials, never replay a stale full list. For an uncertain save/deploy response, inspect current configuration and the saved request/operation before another write. A setting, identity, source, or credential change is new deployment intent.

### Match profiles, permissions, and existing code

| Qualified managed-identity profile | App contract and access |
| --- | --- |
| Blob Storage | Map account URL and container to the app's exact names. Default grant is container-scoped **Storage Blob Data Reader**; writes need explicitly approved **Storage Blob Data Contributor** at that scope. |
| Foundry inference | Select an existing Azure OpenAI-compatible account and model deployment; **Cognitive Services OpenAI User** grants inference. `model` means deployment name, not catalog model ID. Resolve resource-origin versus `/openai/v1/` endpoint shape against the actual SDK; project/agent URLs are not interchangeable. |
| PostgreSQL | Host is required; configure database/user explicitly when the app needs them. Entra mode uses a database role name and refreshed token, not an object-ID username or saved access token. Entra admin, database/schema/table privileges, and TLS remain administrator/app work; ARM Contributor is not database access. |

For the other enabled profiles, read the service-specific prerequisites before configuring: Azure SQL needs an external database user and SQL grants, not just ARM roles; Cosmos NoSQL uses native data-plane grants; Redis needs its data policy, TLS and refreshed tokens; Key Vault needs SDK secret access, not automatic reference resolution. Messaging needs scoped sender/receiver permissions, and Event Hubs checkpoint storage is a separate connection. Application Insights uses a credential-aware server exporter with **Monitoring Metrics Publisher**; a routing connection string does not instrument the app or qualify ingestion. Connector Namespace owns external consent, access policy and triggers; an ARM role on its namespace is not the connection's access policy.

Preserve public sample contracts when converting: Blob uses `AZURE_STORAGE_BLOB_ENDPOINT`, not the generic account-URL suggestion, and performs writes. PostgreSQL requires `PGHOST`, `PGDATABASE`, and `PGUSER`; omit optional `PGSSLMODE` and password rows because that sample enforces TLS in code and rejects those overrides. Migrated Redis uses `REDIS_HOST`, `REDIS_PORT=10000`, generated `REDIS_USERNAME`, and `REDIS_TLS=true`; remove legacy composite `REDIS_ENDPOINT` without an intermediate deployment. Older forks still need their original contract, and mapping a host-only row to the composite name is not equivalent. Key Vault weather reads `KEY_VAULT_URL`, not `KEY_VAULT_URI`. The Outlook migration reads the actual selected UAMI output named by `CONNECTOR_IDENTITY_CLIENT_ID_ENV`; this stores an output name, not a client GUID/token. Inspect the user's revision before applying migrated defaults; do not change app names or authentication merely to match the catalog. AI Gateway remains an explicit manual-configuration exception: the Foundry inference profile is not a gateway route or two-identity chain.

To migrate an exact non-secret manual name, approve removal and save it **without deploying**, then save the matching connection mapping and deploy the complete desired configuration once. The running version keeps its old snapshot during these saves. Do not deploy an incomplete intermediate configuration, silently delete conflicting variables, or move connection credential rows into manual Variables. Unsupported or incompatible integrations keep their existing app-owned configuration until a deliberate supported conversion.

### Select the identity in app code

Each connection chooses one identity; the app can retain several. Only connection-selected UAMIs contribute runtime-only `Identity_<normalized-resource-name>_ClientId` outputs. Read the actual catalog output name and pass it to the native SDK credential, rather than guessing it or submitting a client GUID as an identity selector. Distinct selected identities with the same normalized output name conflict; unselected identities export nothing. An explicit SAMI credential must not accidentally honor an unrelated app-global `AZURE_CLIENT_ID`.

Generated outputs do not change the app-global `AZURE_CLIENT_ID` or adapt a sample that reads only that variable. Configure the sample's documented selection or review per-client SDK changes. Connections/settings/credential snapshots remain version-owned, but assignments are app-wide: each deployment resolves selected identities' current IDs, including retained activation. Missing selected assignments block deployment; identity replacement may require new destination grants. Never store Entra access tokens as credentials.

### CLI configuration and protected-value handling

Check `builder app connections --help`, `add --help`, and the selected service's help. The current public archive includes typed service commands, not the old `--connection-json` add/update contract. Installed help and current target support remain required; do not invent an installer, command, or credential-entry URL when absent.

| Command group | Contract to check in installed help |
| --- | --- |
| `builder app connections list` / `status` | Read saved mappings and configured/missing status; optional `--connection-name` on status. No secret values or connectivity test. |
| `builder app connections add <service>` / `update <service>` | Use `--connection-name`, `--resource` and service-specific values/variable-name overrides. Add infers resource metadata and defaults; update patches supplied typed fields while preserving omitted settings/mappings and unrelated connections. |
| `builder app connections remove` | `--connection-name` removes pending configuration only, not identities/grants. |

Every command needs the exact app's `--name`, `--subscription`, and `--resource-group`. `--resource` accepts a visible resource name or full ARM ID. Name search spans groups in the app subscription; resolve ambiguity interactively, and require a full ARM ID for unattended use. Resource-owned endpoints/hosts are inferred; app-specific container/database/user/model/entity choices remain explicit. Optional rows stay omitted unless their value or `--<setting>-variable` override is supplied. Keep an override next to its setting in examples. Add/update preserve other connections/manual inputs under the current ETag; conflicts require fresh read/reconciliation, not removing the precondition.

For example, after reviewing the target, identity assignment and exact sample mappings, check `builder app connections add storage-blob --help` before:

```shell
builder app connections add storage-blob --name "<app-name>" --subscription "<subscription-id>" --resource-group "<resource-group>" --connection-name "<connection-name>" --resource "<storage-account-arm-id>" --account-url-variable AZURE_STORAGE_BLOB_ENDPOINT --container "<container-name>" --identity system
```

Typed `--identity system` enables/selects SAMI; a UAMI name or full resource ID resolves/attaches/selects an existing identity. Its separate assignment operation finishes before connection save and does not deploy. `--identity none` on update selects credential/app-owned authentication. Disclose and authorize assignment effects, preserve unrelated identities, and re-read after partial failure. Connection removal does not remove identity assignments. The connection save itself does not grant destination access or deploy; current typed CLI commands provide role/administrator instructions, not `--grant-access` or automatic permission grants. Blob writes need an explicitly approved container-scoped Contributor grant; PostgreSQL users/privileges and other service grants remain separate administrator/app work.

**Never put API keys, passwords, protected connection strings, or tokens in connection JSON, command arguments, generated scripts, source, or logs.** Prefer explicit managed identity. With identity omitted, eligible profiles choose protected-credential mode: typed Blob/Foundry commands can retrieve a missing resource key through the caller's ARM permission when local auth is available, then submit it only via the write-only connection save. This is credential retrieval/transfer, not discovery; disclose it and obtain explicit scope before invoking that mode. Do not perform key reads manually or broaden permissions to repair a denied key request. Output can report `credentialSource: "resourceKey"` but never the value. PostgreSQL passwords and unavailable/denied keys remain missing and use the returned Portal handoff.

Stored-value access requires app-scoped `listVariables/action`; Builder CLI has no secret-reveal command. Portal Variables/credential details can use ARM `listVariables` and hold current values briefly in mounted page memory while display stays masked. **Show value** displays the selected row; **Hide value** hides it, and navigation/account changes clear page data. A masked UI is not proof plaintext was never read. Do not open a privileged value view as routine discovery, log/cache its response, or treat its current values as historical/draft snapshots. Review **Replace value** as a separate write-only edit, and discard a replacement without changing the saved value when cancelled.

Connection-owned settings, protected values, and generated identity outputs reach server runtime only, never builds or static frontends. Ordinary manual variables remain build-visible. Save/rotation does not change the running version; a new deployment captures the desired snapshot, retained activation keeps historical selections/credentials, and **Not tested** remains until the deployed app performs a bounded operation. Missing or unreadable required credential status blocks submission, not a reason to reveal or copy a value.

Managed identity is documented for Preview: system-assigned, user-assigned, or both, configured through Portal or ARM, or documented CLI commands when present in installed help. Prefer it when the destination supports Microsoft Entra data-plane authentication and the application's SDK can request the correct token audience. A Portal identity blade, accepted ARM identity property, or successful local developer sign-in does not prove the deployed runtime can obtain a workload token or access the destination. Managed Entra visitor authentication is a different feature and does not grant the backend model access.

If the user's policy requires passwordless access, first verify the identity, SDK, destination roles, and network path; do not quietly substitute a key if those requirements cannot be satisfied. Private networking and automatic Key Vault variable references remain unsupported. For a destination without compatible identity authentication, offer only an explicitly approved service-supported server-side credential, subject to the variable-exposure limits below; do not weaken the service's policy.

## Configure and verify workload identity

Discover existing assignment and non-secret identity metadata before proposing changes. Identity assignment and destination role grants are separate permission changes, not authorized by a request to inspect resources or deploy source. Explain the exact app, identity, destination scope, and save/deployment effect; obtain explicit authorization and leave Portal consent to the human. Check `builder app identity show --help`, `assign --help`, and `remove --help` before CLI use. Current docs describe these commands, but older installed releases may lack them; use the documented Portal/ARM alternative rather than inventing flags. Assignment defaults to system-assigned; preserve other assignments and remove only explicitly selected identities. Wait for assignment completion before connection selection; separately follow any approved deployment before runtime verification.

In the Portal **Identity** page, enable system-assigned identity or attach the selected user-assigned identities. Adding identities can offer **Save only**; removals require **Save and deploy** in Portal. See the [ARM identity contract](https://builder.appservice.azure.com/docs/reference/arm-api/#managed-identity-contract): identity-only PATCH saves assignments without deployment, including removals. Wait for that save operation before a separately approved redeployment. Portal **Save and deploy** and CLI identity commands save first, then submit deployment; failure of the latter does not undo the assignment. Do not repeat a successful removal to recover failed deployment. Identity-only deployment reuses retained build output; `NoBuildArtifacts` means an initial deployment is still needed, not a successful source build. Inspect committed identity state, separate receipts, and actual runtime access.

Use the identity's **principal ID** for a narrowly scoped destination data role and its **client ID** for user-assigned SDK selection. Management Reader/Contributor access is not model inference or other data-plane permission. Do not invent a universal role or token audience; read the selected service and SDK's current contract. Preserve destination firewall rules and separately owned identities.

For supported Azure SDK credential chains, `DefaultAzureCredential` can use system-assigned identity when `AZURE_CLIENT_ID` is unset, subject to the app's actual credential configuration. It does not transfer the developer's local Azure session. For user-assigned identity, set `AZURE_CLIENT_ID` to its client ID or use the SDK's explicit supported selector. When that variable is unset, Portal **Set as AZURE_CLIENT_ID** can select the attached identity for the same **Save and deploy**. This selection changes version configuration and can build a new version; review source/build effects as well as assignment. Once saved, change or remove the variable on **Variables** and deploy a new version to capture the change. Never assume attaching an identity automatically sets this variable.

Application code may call a reachable Key Vault through its SDK with approved identity and secret-read permission; this is distinct from unsupported automatic `keyVaultReference` resolution. Verify token acquisition and one bounded destination operation from the deployed backend. Successful assignment/deployment alone is not a working integration.

## Discover existing resources before requesting endpoint strings

Use available authenticated Azure/Foundry read tools and their discovered schemas, or an already-installed Azure CLI with help-verified account/deployment listing commands. Never require installation of another tool solely to enumerate resources.

1. Start in the user's selected Azure subscription and tenant. List accessible existing Foundry/Azure OpenAI accounts and projects with non-secret metadata only. Do not limit discovery to the Builder app's resource group: its model may be in another group. Broaden to another subscription only when the user selects it.
2. For a supplied Foundry project URL, resolve the project metadata and its associated model resource/connections. Retrieve only non-secret connection metadata; exclude credentials. A project endpoint, model inference endpoint, and deployment name are distinct. Do not reject the URL and send the user back to the Portal if the available tools can resolve it.
3. List existing deployments for the selected resource, including deployment name, underlying model/version, provisioning state, endpoint/API type, and supported authentication where available. A model catalog entry is not a deployment. Report missing metadata as unknown, not an inferred capability.
4. Show a short choice of compatible deployments and ask the user to select when ambiguous. Match the app's actual API and model requirements before configuring it; do not choose the first listed model. An Azure OpenAI deployment name may differ from the catalog model ID.
5. If discovery is unavailable, fails, or access is denied, state exactly what could not be read. Ask only for the unresolved non-secret identifiers, or guide the user to the exact resource/deployment view. Do not claim no models exist from an empty partial listing, request broader roles, or provision a model to bypass discovery.

Discovery does not authorize model invocation, resource creation, role assignments, key retrieval, or charges. Do not call list-keys or secret-bearing connection operations as a discovery step. Management visibility does not prove data-plane access, network reachability, or inference compatibility.

For Azure MCP, discover the available resource/project read tools first. Where available, Foundry's `model_deployment_get` accepts the discovered `foundryAccountResourceId`; omit `deploymentName` to list deployments rather than guessing a model name. Tool names and schemas can vary by host/version, so inspect the exposed schema before calling. Avoid credential-returning project connection tools.

With Azure CLI already available, inspect `az cognitiveservices account list --help` and `az cognitiveservices account deployment list --help`. List accounts in the selected subscription, project only resource IDs/names/kinds/groups/endpoints, then list deployments on the selected account. This is account/deployment discovery, not complete enumeration of every Foundry project or provider type; use available project metadata tools for the supplied project URL. Neither listing needs a service key.

### Match the selected application's API

The published [AI assistant sample](https://github.com/AzureAppService/app-service-builder-ai-agent) supports OpenAI or Azure OpenAI Responses API text requests, not every model offered by Foundry. Inspect its current README, configuration parser, provider code, and tests before adapting it. For an existing app, preserve its SDK/API unless a change is explicitly chosen.

The migrated Azure provider uses managed identity by default. Set `MODEL_SERVICE=azure-openai`, map the Foundry account endpoint to `AZURE_OPENAI_ENDPOINT` (the SDK accepts the resource origin or supported `/openai/v1/` base), and map the existing deployment to `AZURE_OPENAI_DEPLOYMENT`. Keep `AZURE_OPENAI_AUTH_MODE=managed-identity` and the separate `APP_API_TOKEN` as app controls. The backend calls `/openai/v1/responses` with SDK token acquisition/refresh. A Foundry project URL ending in `/api/projects/...` or an arbitrary inference/chat-completions endpoint is not interchangeable; resolve metadata instead of stripping a project URL or guessing a hostname.

Do not assume this sample's provider code supports token credentials because Builder supports managed identity. Inspect its actual authentication code; a key-based provider needs an explicitly reviewed SDK/code change before using an Entra token provider. Verify endpoint, token audience, deployment/API compatibility, and the selected identity's destination role separately.

Older key-only forks need a reviewed SDK/code migration before selecting Entra authentication; do not assume their code changed with upstream docs. The migrated sample's API-key alternative is an explicit auth-mode choice with protected mapping, not the default or hosted qualification for that mode. Remove old manual endpoint/deployment/key settings only with approval and without deploying incomplete intermediate state; do not provision another model or rewrite unrelated source to match a profile.

The sample also requires `APP_API_TOKEN` for its own `/agent` route. That token, the model provider key, Builder management login, and platform visitor authentication are separate credentials. Do not expose any of them in a frontend. If a browser UI is needed, design a supported backend authentication path rather than shipping the sample bearer token in browser assets.

## Configure without exposing credentials

Use the recommended Connections workflow above for supported service/authentication profiles. Manual Variables is a compatibility fallback, not the default place for service credentials. Explain before any fallback: Builder manual variables are shared with all components during build and with HTTP processes at runtime. They have no runtime-only/per-component scope, and authorized value retrieval can return all desired values. Encryption at rest does not prevent build scripts, frontend bundles, or authorized runtime diagnostics from exposing values. Automatic `keyVaultReference` resolution is unavailable; app-owned SDK access through managed identity is separate.

If the user accepts this development/test boundary, use an existing narrowly scoped test credential they supply securely outside chat. The user can enter it directly on the app's Variables page, or provide an explicitly approved local settings file for the [variable workflow](operations.md#manage-desired-variables). Keep that file outside the repository and build context; never print it, stage it, echo keys in commands, or retrieve keys just to populate it. Do not collect credentials before explaining the limitation.

Set only the approved app's required settings. Review build commands and frontend environment handling before passing a key to a combined app; never use public/client-prefixed variables for secrets or assume a backend-only variable scope exists. If exposure cannot be ruled out for the proposed build, stop credential configuration and choose a safer design. A separate approved new build/deployment must capture the desired variables; retained versions keep their historical values.

## Verify the integration, not just liveness

Use mocks for local tests until the user authorizes a real model call and its external charges/data handling. After deployment, verify the active version and HTTP behavior, then make one bounded authenticated request with non-sensitive input to the app's actual model route. For the published assistant, `GET /health` proves process liveness only; it does not contact the provider.

Report app serving and model integration separately. A 401, 403, incompatible API/model response, timeout, or unreachable dependency is an integration failure, not a successful assistant. Preserve sanitized status and error details without prompts, keys, or full provider responses; do not fabricate replies, open firewalls, or widen permissions to make the check green.
